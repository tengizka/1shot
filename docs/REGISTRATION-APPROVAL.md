# Очное подтверждение регистрации — восстановленный черновик

## Состояние выпуска

Исходники и тесты восстановлены заново после обнаруженного расхождения checkout. Это не восстановление прежних файлов побайтно: реализация повторно проверяется на текущем дереве. SQL и функции Supabase **не применены к рабочему клубу**, установленный Desk не заменён.

Новая форма находится в `release/registration/`. Корневой `index.html` её не подключает, поэтому публикация исходников не включает новую регистрацию в мини-аппе раньше обновления сервера. `Stage-Frontend.ps1 -OutputDirectory <новая папка>` через PowerShell готовит отдельную копию фронтенда для тестирования, не меняя исходный index, настройки или живые сервисы. Это **не** установщик большого выпуска.

## Протокол

1. `register_application` проверяет подпись Telegram и обязательные поля. Пароль 1–64 символа, не целиком пробельный. Анкета шифруется AES-GCM с ID заявки в AAD. Пароль не включается в сводку.
2. Приватная `club_registration_requests` отделена от очереди автоматического входа. Одна активная заявка на Telegram, включая `attention`; повтор возвращает тот же ID, не меняя исходную анкету/пароль; не более трёх новых анкет в сутки. Создания Gizmo и записи профиля при отправке нет.
3. Desk получает сводки в существующем `club_worker_poll`. Гость получает только собственный статус внутри уже существующего запроса capabilities; отдельного HTTP-таймера нет. Это не гарантирует общий месячный лимит всей организации.
4. Администратор очно сверяет личность, отмечает проверку и отдельно подтверждает создание. Статус lease проверяется сервером и перед внешними записями. Чекбокс не заменяет авторизацию: API доступен доверенному Desk по секрету агента.
5. До claim сохраняется локальное намерение. Claim одноразовый, шифротекст в облаке уничтожается. Проверяются дубли ника и телефона (8/7 нормализуются). Возраст — на текущую дату Москвы; группа 18+ / Клиенты определяется по точному имени, ID не угадывается. Гости не удаляется и не используется.
6. Новый положительный целочисленный UID журналируется до установки пароля. Сверяются поля созданного профиля, группа, дата рождения и результат проверки пароля. SQL finish атомарно связывает профиль; чужая существующая связь не перезаписывается.
7. При неопределённости — `attention`. Автоматического повтора создания или парольной записи нет. Сохранённый подтверждённый результат можно отправлять повторно без повторного изменения Gizmo; конфликт статуса требует разбора. Локальный журнал не содержит паролей, анкет, шифротекста или сырых ошибок Gizmo.

Автоматическое создание отключено в новом encrypted worker, LegacyBridge и старом agent.py. Уже установленные старые версии **не выключаются** от изменения исходников. До миграции надо остановить/обновить все такие процессы и сверить незавершённые записи. Обычный вход отдельный, политика паролей операторов не ослабляется.

## Сроки и неопределённые результаты

Ожидающая анкета действует 72 часа; затем личные данные и шифротекст очищаются. При done/rejected личные данные также очищаются. Терминальные строки удаляются через 7 дней. Это запросная очистка, не фоновое стирание в точную секунду и не удаление из резервных копий.

Processing старше 15 минут становится attention; новая анкета блокируется. Attention сохраняет сведения для сверки до ручного разбора. Для случаев, когда гость может сам успешно войти, добавлен интерфейс сверки и миграция 015: см. REGISTRATION-RECONCILIATION.md. Случаи без подтверждённого входа по-прежнему блокируются. Нельзя удалять журнал, сбрасывать processing или повторять создание «на удачу». При известном UID сверяют именно его; если UID неизвестен — проверяют фактические записи Gizmo. Сам телефон не доказывает право на аккаунт. Нельзя объявлять операцию успешной без проверки профиля и пароля.

## Что нужно до включения

- Подготовительный Prepare-Upgrade.ps1 с проверяемой локальной копией реализован, но требуется полноценный единый PowerShell-upgrade с резервированием .env, настроек, SQLite (с учётом WAL), безопасной остановкой старого Desk, проверкой состояния/контрольной суммы миграции и проверкой результата.
- Миграция 014 транзакционная, но НЕ повторяемая. Она отказывает при живой lease и свежих pending/running auth. Самостоятельно повторять SQL нельзя; будущая автоматизация должна проверять журнал миграций. Guard не доказывает отсутствие старого отдельного legacy-agent: это проверяется при остановке.
- Порядок: подготовка/резервирование и остановка → сверка старых операций → 014 → функции auth/bookings/desk → новый Desk и проверка → подключение новой формы. Не развёртывать новый bookings до SQL.
- Проверить реальные группы и разрешённую длину пароля на установленном Gizmo. Моки не подтверждают его политику.
- Завершить обработку оставшихся случаев attention без успешного входа гостя. Создание Gizmo и запись PostgreSQL не атомарны между собой.
- Local bootstrap пока не устанавливает 014. Формат переноса v1 не содержит очередь: экспорт/импорт теперь отказывается работать при обнаружении новой таблицы, даже пустой. Перенос с Supabase не возобновлялся.

Остальной большой редизайн, самостоятельный выбор нового пароля после разрешения администратора и полная автоматизация выпуска остаются отдельными незавершёнными задачами.

## Проверка этого дерева

Локально: 99 Python-тестов, 35 Deno/SQL/server-тестов, семь браузерных сценариев (registration-approval, desk-stability, desk, admin-tools, desk-availability, economy, polish). Typecheck изменённых Edge-функций и локального сервера пройден. Новый браузерный тест загружает staged-форму специально; обычный index остаётся прежним. Windows CI дополнительно собирает и запускает приложение и проверяет PowerShell-подготовку изолированной формы. Результат CI относится к конкретному коммиту, а не к живому Gizmo.
