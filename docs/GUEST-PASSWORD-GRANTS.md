# Пароль задаёт владелец: черновик протокола 016

Код и изолированные тесты готовы; рабочие функции/БД/Desk НЕ обновлены. Новая форма находится только в staged-копии `release/registration`, корневой index её не подключает. Это не готовность всего большого выпуска.

## Доступные сценарии

- Владелец уже связанного Telegram-профиля отправляет запрос из профиля или кнопкой «Забыли пароль?» на staged-экране входа. Даже без локально сохранённого профиля сервер берёт аккаунт из ранее проверенной связи Telegram, а не из телефона/UID в запросе.
- Для спорной регистрации с **известным созданным UID** администратор может выдать разрешение прямо из карточки. Реальные поля Gizmo должны совпасть с анкетой и локальным известным UID. Для неизвестного UID кнопка не появляется: угадывать аккаунт нельзя.
- Администратор проверяет личность и конкретный аккаунт, отдельно подтверждает разрешение на 10 минут. Для служебной/неизвестной/неоднозначной группы нужно дополнительное подтверждение. В Desk поле нового пароля скрыто и отключено, старые публичные методы App.reset_password/reset_password_request отказывают без записи в Gizmo.
- Владелец вводит пароль только в мини-аппе. Для однозначно подтверждённых гостевых групп минимум один непробельный символ; для служебных/неизвестных — минимум восемь. Максимум 64 Unicode-символа. Пробелы внутри пароля допустимы, полностью пробельный запрещён.

## Границы разрешения

Приватная таблица связывает разрешение с Telegram, неизменным UID, ником, группой, минимальной длиной, исходной заявкой и выдавшим worker. Одно активное разрешение на аккаунт и Telegram; attention также блокирует новые разрешения. Повтор выдачи возвращает существующее разрешение, не продлевая срок. При отправке повтор того же request_id не заменяет пароль; другой request_id после приёма отвергается.

Публичный endpoint проверяет подписанный Telegram. Нельзя передать чужой UID, номер телефона или изменить целевой аккаунт в запросе установки. Пароль шифруется AES-GCM, отдельный домен ключа, AAD включает grant_id и request_id. Сводки и локальный журнал не содержат пароль/шифротекст. Claim забирает шифротекст один раз и переводит разрешение в processing. Done выставляется только после проверки входа с новым паролем.

До внешнего действия проверяются реальный профиль, группа и политика; изменение группы на более привилегированную блокирует запись. Активная игровая сессия блокирует выдачу/исполнение — её завершает только сам владелец, никаких команд logout/lock из этого обработчика нет. Сам пароль меняется **одним** POST, без промежуточного пустого пароля, и затем проверяется по точному UID.

До claim сохраняется локальное намерение. После сбоя создание/парольная запись не повторяется. Повторяются только сохранённые результаты; конфликты владельца/lease останавливают автоматические отчёты. После перезапуска нельзя считать новый worker старым владельцем операции.

## Неопределённый результат

Processing старше 15 минут переводится в attention запросной очисткой. После неопределённой записи новый пароль вслепую не отправляется. Если гость может успешно войти, Desk предлагает отдельную сверку доступа:

1. Нужен успешный вход того же Telegram в тот же UID после ошибки, не старше 10 минут; legacy/незавершённый/чужой вход не подходит.
2. Проверяется текущая связь профиля и конкретный аккаунт; администратор повторно подтверждает личность, для служебной группы — дополнительные права.
3. Попытка получает статус **resolved, не done**. Это подтверждение доступа, а не утверждение, что введённый новый пароль установился. Повторной записи в Gizmo нет. Доказательство используется одноразово, повтор завершения идемпотентен.

Если ни старый, ни новый пароль не позволяют войти, автоматического обхода нет: нужна ручная сверка фактического состояния Gizmo. Если UID созданного аккаунта неизвестен, восстановление через этот механизм пока недоступно. Новая привязка существующего аккаунта к другому Telegram без прежней связи также не реализована — телефон не является основанием для захвата аккаунта. Fallback установки пароля с игрового ПК не заявляется: поддержка конкретного Gizmo не подтверждена.

## Опрос и хранение

Сводки для Desk включены в существующий worker_poll, данные владельца — в capabilities/state. Отдельного HTTP-таймера для паролей нет. Вызовы авторизации/claim/finish — дополнительные операции, поэтому это не гарантия общего лимита 500k.

Неполученные authorized/queued разрешения истекают через 10 минут, шифротекст очищается. При claim он удаляется из БД; при done/resolved/expired очищается также ник. Терминальные строки удаляются через 7 дней запросной очисткой, не точным фоновым таймером. Attention сохраняется для сверки. Аудит разрешения неопределённой попытки хранит только ID и время, пока без автоматического удаления.

Мини-апп очищает поле при отправке. В sessionStorage остаётся только отметка попытки по ID, не пароль. При неоднозначной сетевой ошибке повтор ввода этим разрешением блокируется до результата/истечения; новое разрешение требует администратора. Это намеренный отказ от рискованного повторного изменения пароля.

## Выпуск и проверки

Требуются 014 → 015 → 016, обновлённые функции, новый Desk и только затем staged-фронтенд. Старые процессы необходимо остановить: изменения исходников сами их не отключают. PowerShell Stage-Frontend включает оба новых экрана, Prepare-Upgrade учитывает все три миграции; он по-прежнему лишь делает защищённую локальную копию/план и не применяет SQL. Полный согласованный updater, резервная копия облака и проверенная история миграций ещё не реализованы.

Локально прошли 123 Python-теста, 37 Deno/SQL/server-тестов и шесть браузерных сценариев. Проверены чужой владелец/UID, подтверждения, минимум служебной группы, смена политики, AES/AAD, истечение, одноразовость, потеря ответа без повторной записи, отсутствие logout, privacy сводок, отказ старых методов Desk, восстановление UI после перезагрузки и сверка доступа. Windows CI дополнительно проверяет сборку, запуск и PowerShell-preflight. Реальную поддержку длины/символов пароля в установленном Gizmo ещё надо подтвердить на месте.
