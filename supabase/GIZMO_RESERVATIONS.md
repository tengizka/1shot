# Текущее подключение броней — агент v3.1, контракт из docs.json

## Что подтверждено спецификацией

- `PUT /api/reservations` создаёт бронь, `POST` обновляет существующую.
- Параметры — query: Date, Duration, UserId, Note, Hosts, Users.
- `ReservationHostParameter.hostId` — внутренний ID хоста Gizmo, не номер ПК.
- `ReservationUserParameter.userId` — ID пользователя Gizmo, не Telegram ID.
- Результат PUT — числовой ID; также поддержана обёртка result.
- `GET /api/reservations/{reservationId}` возвращает date/endDate, hosts и users.

Для Hosts остаётся индексированная query-запись `Hosts[0].HostId`.
Вложенные `Users[0].UserId` и необязательный `PreferedUserId` исключены после
ответа Gizmo `UserMember Id 0 not found`: причина нулевого ID не доказана, но
разбор этих вложенных полей больше не нужен. UserId верхнего уровня остаётся
положительным ID из profiles, предварительно проверенным GET /users/{id}.
После создания пользователь добавляется отдельным документированным методом
PUT /reservations/{reservationId}/users/{userId}. Затем проверяется readback.
Сам OpenAPI не описывает сериализацию вложенных объектов полностью; всё ещё
нужна проверка одной тестовой брони на реальном сервере.

**В docs.json НЕ указаны единицы Duration.** Агент определяет секунды/минуты
по существующим броням: сравнивает endDate-date с duration. Противоречивые,
отсутствующие или неподдерживаемые данные блокируют создание, без угадывания.
Date передаётся из created_at исходной заявки, длительность — 60 минут.
Таким образом, задержка очереди не добавляет ещё один час.

## Установка

Схема Supabase из прошлых исправлений остаётся: reservations.telegram_id →
profiles.telegram_id, SQL-функция reserve_club_host, срок 1 час и price=0.
**Новых SQL-миграций в этом обновлении нет.**

1. Supabase → Edge Functions → pending-reservations: заменить код файлом
   `functions/pending-reservations/index.ts` и Deploy. Эта версия добавляет в
   очередь gizmo_user_id из profiles. Verify JWT выключен, x-agent-secret проверяется.
2. Остановить прежний агент. Скачать свежий agent.py. Работать должен только
   **один экземпляр**. В баннере новой версии: `v3.1 — PUT + explicit user link`.
3. В папке агента выполнить:
   ```powershell
   python agent.py --check-reservations
   ```
   Это только чтение Gizmo, новых броней или изменений в Supabase не делает.
   Ожидаемый результат: `Duration за 60 минут = 60` либо `= 3600`, в зависимости
   от единиц сервера. Код не предполагает заранее ни одно из этих значений.
4. Если данных нет: вручную в Gizmo Manager создать одну контрольную бронь с
   известными временем и длительностью на выбранном тестовом ПК. Снова выполнить
   проверку. После проверки завершить/отменить эту контрольную бронь вручную.
5. Запустить `python agent.py`, сделать одну новую бронь в мини-аппе.
6. Успех агента: `Gizmo бронь <ID> проверена: окончание ...`. Он проверяет ID,
   хост, пользователя и обе даты чтением созданной брони, прежде чем подтвердить её.

## Защита от повторного создания

Рядом с агентом появится **agent-reservations.json**. Не удаляйте и не переносите
его отдельно от агента. Это журнал состояния, без паролей и секретов. Намерение
отправки записывается до PUT. При перезапуске та же заявка не отправляется повторно.
Запуск копий агента из разных папок или одновременно всё ещё небезопасен —
распределённой блокировки очереди на сервере пока нет.

Если запись подтверждена локально, но PATCH в Supabase не прошёл, агент повторит
только PATCH. При HTTP 400/другом определённом отказе создаётся failed.
При сетевом сбое PUT, HTTP 5xx, отсутствии ID или ошибке проверки результата —
uncertain в журнале, Supabase-заявка остаётся pending до истечения часа. Нужна
ручная проверка в Gizmo по ID либо по Note `1SHOT app request=<UUID>`.
Не создавайте новую заявку на тот же ПК до выяснения результата uncertain.

## Границы проверки

Тесты локальные, запросы к реальному серверу клуба не выполнялись. Неизвестные
значения ReservationStatus 0/1 для автоматической отмены не используются.
Ручные административные блокировки не снимаются. Автоосвобождение по окончании
нативной брони следует проверить в Gizmo Manager. При неправильных датах readback
агент не подтверждает бронь, но сам её не отменяет: требуется администратор.

Метод чтения баланса также найден в спецификации: GET /api/users/{userId}/balance.
В это обновление подключение баланса не входит.

## Обновление v3 → v3.1 после ошибки UserMember Id 0

Заменяется только agent.py. pending-reservations из v3 и SQL менять не нужно.
Сохраните рядом agent-reservations.json и запустите один экземпляр нового агента.
До создания GET /users/{id} должен подтвердить аккаунт; при ошибке запись брони
не отправляется. В лог выводятся hostId/userId/Duration без имени и пароля.

После создания возможна частичная ошибка при отдельной привязке пользователя.
В этом случае сохраняется ID созданной брони в журнале uncertain; заявка НЕ
подтверждается, повторное создание автоматически НЕ выполняется. Администратору
нужно проверить указанную бронь вручную перед новой попыткой. В ошибке теперь
остаётся точная стадия/причина проверки, а не только общий текст.
