# Поэтапное включение окна техработ

Backend подтверждён пользовательским запросом: HTTP_OK, protocol=2, desk.online=true, valid_for_ms=25980. Первая автоматическая проверка вернула VERIFY_FUNCTION, но повторная read-only проверка подтвердила новое поле; повторное развёртывание не требовалось. Причина первоначального сбоя проверки не установлена.

Frontend подключает desk-availability.js/css: блокирующее окно при истечении lease, автоматическое восстановление, отдельная индикация ошибки связи. Для вошедших пользователей heartbeat включён в существующий state (один запрос/5с), для гостей проверяется capabilities. Скрытые страницы не опрашивают сервер; при возвращении требуется свежий ответ. Истечение контролируется локальным таймером, без доверия часам телефона. Данные и команды не изменяются, выход из Desk проверяется по существующей lease (до 30с); сворачивание в трей не отключает heartbeat.

`Update-Desk-Maintenance.ps1` (Windows PowerShell 5.1/7, x64) скачивает CLI 2.119.0, проверяет закреплённую SHA256, скачивает два файла из закреплённого коммита и обновляет **только club-bookings** через remote bundler. Docker и SQL не используются. Конфигурация Desk, секреты проекта, данные и другие функции не изменяются.

Для операции нужен личный access token аккаунта Supabase, имеющего доступ к проекту `zqhfvtgktbfnxcclqqny`. Создаётся пользователем в https://supabase.com/dashboard/account/tokens; вводится скрыто только на его ПК. Не присылать токен, пароль БД или service-role key в чат. Token передаётся CLI через временную переменную окружения процесса, не через аргументы и не записывается скриптом на диск. Старое значение окружения восстанавливается, временные файлы удаляются. После успешного обновления одноразовый token можно отозвать.

Успех: `DESK_MAINTENANCE_BACKEND_READY`. `DESK_OFFLINE` после него — корректный результат обновления при остановленном Desk, а не ошибка установки. Проверка не включает бронирования и не запускает команды на ПК.

Если `UPDATE_FAILED`, остановиться и передать только название этапа. Не повторять обновление вслепую. При ошибке VERIFY_FUNCTION функция могла уже обновиться: это не означает откат. Сначала проверить ответ capabilities.

После подтверждения backend нужно отдельно опубликовать frontend с окном. Не публиковать блокирующий frontend раньше backend: в старом ответе нет поля desk. Новый SQL/новая сборка Desk не нужны.

Проверки: Windows mocked helper tests (5.1/7), изолированные тесты lease/HTTP в `server/tests/local.test.ts`. Эти проверки не доказывают успешное развёртывание в рабочем Supabase — нужен результат пользовательского запуска.
